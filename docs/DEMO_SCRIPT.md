# Демонстрация DOOMSDAY за пять минут

Сценарий для одного выступающего. Весь питч, действия и ожидание ответа укладываются
в **4:45**, резерв — **0:15**. Вступление и завершение находятся в [PITCH.md](PITCH.md).
Не запускать установку модели или загрузку весов во время выступления.

## Подготовка до таймера

1. Запустить модель, SSH-туннель, backend и frontend по проверенному пути из
   [README](../README.md) и [BREV_SETUP.md](BREV_SETUP.md). GPU должен быть доступен
   именно в окно демонстрации. Время выступления пока не сообщено; стоп-код
   подтверждён на **8 ноября 2026, 12:00, Asia/Almaty (UTC+5)**.
2. Проверить реальный маленький inference через существующий smoke. `/api/health`
   со статусом `ready` проверяет конфигурацию и не заменяет успешный запрос к модели.
   Ключи не показывать на экране; закрыть `.env`, консоль с секретами и лишние вкладки.
3. Подготовить отдельную демонстрационную SQLite-базу и её резервную копию.
   Официальную конфигурацию `codex_context/checklist.json` и исходные восемь
   критериев не менять. Для первого показа нужна эта конфигурация; новая настройка
   сохраняется отдельной версией. Не проводить репетицию на базе сдачи.
4. Импортировать через «Загрузка диалогов» публичный `codex_context/eval/synthetic_dialogue.json`
   либо использовать уже проверенную копию этого тестового диалога. Убедиться,
   что видна отметка «Тестовый диалог». На проекторе не открывать частные DEV/PROD.
5. Подготовить сохранённые реальные оценки этого публичного примера: исходные
   восемь критериев и результат с демонстрационным девятым. Они нужны для fallback.
   Такие сохранённые оценки и база находятся локально, не входят в Git; после
   чистого клонирования их следует создать настоящим проверочным запуском.
6. Проверить заранее N/A, evidence, открытие формы апелляции и редактора критериев.
   Иметь под рукой два [публичных скриншота](images/) как последний резерв.

Для чистой демонстрационной базы используется проверенный запуск backend
без импорта частного DEV; каталог должен быть новым:

```bash
backend/.venv/bin/python -m backend --host 127.0.0.1 --port 8000 \
  --no-dev --db artifacts/demo/rehearsal-NEW/app.sqlite3
```

Затем загрузить указанный публичный JSON через интерфейс. В текущей рабочей
копии сохранённый fallback есть в
`artifacts/brev/final-delivery-20261108/demo.sqlite3` (вне Git). Его не подменять
базой свежего live-показа: там уже есть две версии и проверочная апелляция.

## Основной показ

| Время | Действие | Что показать или сказать |
|---|---|---|
| 0:00–0:25 | Открыть реестр и тестовый диалог | Вступление из PITCH. «Это публичный синтетический пример; будем показывать процесс, а не измерять accuracy». |
| 0:25–1:10 | Выбрать официальный чек-лист и один раз нажать «Оценить» | Новая job и настоящий ответ Qwen3-14B-AWQ. Пока идёт запрос, объяснить: модель выбирает ответы, код валидирует и считает. На ожидание отводится не более 35 секунд. |
| 1:10–2:00 | Открыть evidence, затем N/A и итог | Нажать ссылку реплики, показать подсветку исходного текста/проверенный участок. На проверенном примере критерии потребности и идентификации имеют N/A с причиной. Показать применённый вес и отдельный критический флаг. |
| 2:00–2:55 | Подать апелляцию и принять решение | Выбрать 04, «Подать апелляцию» → комментарий → «Отправить апелляцию» → «Рассмотреть». Для инженерной проверки выбрать «Изменить оценку», ступень 20 → 15 и указать проверочный характер решения. Сохранить; сравнить исходный и итоговый результат. |
| 2:55–4:10 | Изменить чек-лист отдельной версией и применить | «К чек-листам» → «Добавить критерий». Ввести проверочное условие из раздела ниже, вес 3, сохранить новую версию. | 4:10–4:30 | Открыть историю, затем файлы сдачи | Переключить исходную оценку: её версия и решение по апелляции сохранены. Показать `results/dev/results.json`; состояние контрольного файла назвать фактическим, без подмены DEV. |

Итого: 25 + 45 + 50 + 55 + 75 + 20 + 15 = **285 секунд**, резерв 15 секунд.
Во время показа максимум два новых оценивания. При ошибке не запускать цепочку
повторов и не продлевать выступление.

## Проверочная апелляция и новый итог

Текст комментария и причины должен явно содержать:

> Синтетическая техническая проверка пересчёта в демонстрационной базе, не Ground Truth.

При выборе «Изменить оценку» указать ответ 15, объяснение проверочного характера,
реальные evidence из тестового диалога и проверенный диапазон. Не утверждать,
что инженерная замена исправляет реальную ошибку модели или является ручной GT.

В уже проверенной копии настоящего результата публичного примера исходный итог
был 100, после замены ступени 04 с 20 на 15 стал **92,31**. Общий scorer
воспроизвёл пересчёт; оригинал, metadata и результат после reload сохранены.
Это пример с конкретными N/A и весами. В другом результате не обещать заранее
то же число — показывать фактически рассчитанный итог.

Если выбрано решение «Подтвердить оценку», итог может остаться прежним. Нельзя
называть это изменением балла; для демонстрации численного пересчёта предназначен
явно обозначенный инженерный сценарий выше.

## Проверочный новый критерий

- Название: «Синтетический: оператор указал раздел „Помощь“».
- Тип: бинарный; вес: 3; N/A выключен.
- Формулировка: «СИНТЕТИЧЕСКИЙ ПРОВЕРОЧНЫЙ КРИТЕРИЙ. Проверьте только наличие
  слова „Помощь“ в исходных репликах оператора без учёта регистра. yes — есть;
  no — нет. Не оценивайте продуктовые факты. Укажите реплику-доказательство».

Это воспроизведение проверенного теста динамической конфигурации. Условие не
содержит conversation_id и не меняет исходные восемь бизнес-критериев.
В проверенном запуске новая версия содержала девять критериев, модель вернула
результат и по добавленному условию. Во время защиты показывать фактический ответ,
не редактировать его ради ожидаемого балла. Демонстрационную версию не использовать
для официального восьмикритериального экспорта.

## Если модель недоступна или задержалась

В течение первых 35 секунд ожидания переключиться на сохранённую проверенную
оценку того же публичного синтетического диалога и сказать:

> Сейчас показываю сохранённый результат настоящего прошлого вызова. Новая оценка
> в этой части показа не получена.

Далее сохранить общий тайминг: evidence → N/A → апелляция с локальным пересчётом
→ редактор версии. Для применения изменённого чек-листа открыть сохранённую
оценку девяти критериев и назвать её сохранённым результатом. Текущее изменение
правила без доступной модели не выдавать за новое оценивание.

Просмотр результатов, история, решения по апелляциям и пересчёт из сохранённых
ответов работают без inference. Новый запуск оценки требует модели. Если
недоступен и локальный backend, открыть [evidence](images/demo-evidence.png) и
[пересчёт](images/demo-appeal-recalculation.png); это скриншоты, а не живое приложение.

## После показа

Сохранить результаты и журнал сессии. Остановить или удалить созданный GPU и
ненужный диск по текущему плану ресурсов; проверить фактический статус API,
а не только успешный выход CLI. Закрыть туннель и ненужный backend. Не удалять
базу результатов, исходный DEV/PROD и чужие ресурсы.

Для контрольной сдачи использовать [SUBMISSION.md](SUBMISSION.md). Час включает
получение настоящего PROD, inference, экспорт, проверку JSON, commit и push.
Отсутствующий контрольный набор — внешний блокер, не повод создавать фиктивный
`results/prod/results.json`.

## Что уже проверено

- Browser live: 8/8, два реальных inference-запроса, без mock API.

- Отдельный синтетический UI-change: пять проверок, 100 → 92,31,

- Эти проверки не являются независимой человеческой разметкой и не измеряют
