# Состояние backend DOOMSDAY

Обновлено: 7 ноября 2026. Рабочая ветка: `feat/backend`. Основная реализация
`7ecfed0` отправлена в GitHub; интегратор уже объединил её в `main` через
[PR #2](https://github.com/syngyskadyr/DOOMSDAY/pull/2), merge `8459ea6`.
Новых объединений backend-участник не выполняет.

## Работает

- Все операции HTTP API v1: импорт, список/карточка, фильтры, версии чек-листов,
  фоновые оценки, апелляции и атомарный пересчёт.
- SQLite сохраняет диалоги, задачи, оригинал/финал, версии и журнал решений.
  Зависшие задания после перезапуска становятся failed без повтора модели.
- Адаптер вызывает `validate_response`, затем общий `calculate_score`.
  Исторические результаты используют свой `checklist_snapshot`; Decimal
  преобразуется в JSON number, неизвестные значения остаются null.
- Backend читает корневой `.env` или `--env-file`, с приоритетом окружения
  процесса. `--no-env-file` отключает чтение; значения не интерполируются.
- Публичная сборка подключается `--frontend <каталог>` и раздаётся с API на
  одном origin. Явно несуществующий каталог даёт понятную ошибку запуска.
- `/docs` содержит JSON-редакторы POST-запросов и синтетический пример импорта.

## Проверено

На предыдущем этапе прошли 37 backend-тестов и 34 существующих ML-теста.
Проверено по настоящему HTTP: импорт 65 DEV, повторный запуск без дубликатов,
список, карточка, чек-лист, 503 без провайдера, 404 для приватных путей.
DEV, SQLite, результаты и секреты исключены Git; проверен состав `7ecfed0`.

На текущем этапе прошли **53 backend-теста**: 22 HTTP API, 1 последовательный
demo flow, 13 загрузки окружения, 2 Swagger/frontend handoff, 6 импорта и 9
адаптера. `pip check` успешен. Все модельные зависимости в тестах синтетические;
настоящие ML-валидатор и scorer используются без сети. 34 прежних ML-теста
повторно не запускались: ML-код не менялся, используется результат прошлого этапа.

Последовательный flow подтвердил: новый разговор → оценка v1 → evidence по
message_id → апелляции change/confirm → новая версия с новым критерием и правилом
→ оценка v2 → новый экземпляр backend на той же SQLite. Обе оценки, снимки,
оригинал/финал, версии и два решения сохранились без повторного вызова оценщика.
Это проверка API, а не демонстрация настоящего UI или качества модели.

Обновлённый CLI фактически запущен на 127.0.0.1:8000, повторный импорт пропустил
65 DEV. Настоящим HTTP проверены health (unavailable без провайдера), список,
чек-лист, пять JSON-редакторов POST в OpenAPI, `/docs` (200), приватные пути (404).
Окружение и runtime-данные не выводились. Проведён аудит публикуемых файлов:
реальных DEV-реплик, исходных audio_url, ключей и баз в изменениях нет.

## Внешние блокеры

1. На GitHub проверены `main`, `feat/backend`, `feat/cqa-evaluator`: frontend
   отсутствует во всех деревьях. Нужны ветка/сборка frontend и её команда сборки.
2. В окружении нет `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_STYLE`;
   корневой `.env` отсутствует. ML-участник должен настроить провайдера и сообщить
   готовность к одному реальному запуску. Backend не выбирает модель/тариф сам.

Командные `HTTP_API_CONTRACT.md` и HTTP fixtures доступны локально как исходные
неотслеживаемые материалы, но пока не опубликованы в GitHub. Они не изменяются
backend-участником; интегратору нужно опубликовать согласованный комплект.
Запуск и краткая карта API описаны в `backend/README.md`, интерактивные запросы
доступны в `/docs`, поэтому отсутствие комплекта не блокирует сам сервер.

## Следующий шаг

Доступные проверки текущего этапа завершены. Отправить backend-коммит и PR.
После публикации frontend запустить его сборку через `--frontend` на том же
компьютере; API base — относительный `/api`. После настройки провайдера выполнить
одну оценку через POST backend, проверить evidence по messages, подать/рассмотреть
апелляцию, изменить чек-лист и проверить новую оценку/историю после перезапуска.
До снятия этих двух блокеров цель совместной демонстрации не считается достигнутой.
