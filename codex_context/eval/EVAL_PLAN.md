# План проверки оценщика

## Что проверяем

Проверки формата, правил и арифметики выполняются отдельно от оценки качества решений ИИ. Источники: пользовательский `invoke.json` и чек-лист `CQA_Chat_Quality_Checklist 1.pdf`, стр. 1–3. В исходном JSON нет эталонных ответов. Близость к будущему GT организаторов нельзя измерить по неразмеченному DEV; приведённые ниже метрики — наши инструменты разработки.

## 1. Формат и правила

- Проверить JSON, версию чек-листа, уникальность критериев и наличие ровно одного результата на каждый критерий текущего конфига, включая добавленные.
- Проверить типы и `allowed_answers`. Для 04 допустимы только 0/5/10/15/20, для 06 — 0/4/7/10. Нельзя усреднять ступени: ответы 7 и 10 не превращаются в допустимые 8.5.
- N/A допустим только при разрешении и выполнении условия. Недостаток внешних фактов, ошибка API или обрезанный ввод не становятся N/A. Если требуемая идентификация не подтверждена, для 03 действует `no`.
- Присвоить `m001…` по исходному индексу `transcript`: индекс 0 → `m001`. Делать это до фильтрации; сохранять bot/system и исходные timestamps. Каждая ссылка должна вести в тот же диалог; цитата должна совпадать с источником.
- Проверять, что evidence действительно обосновывает вывод. Действия бота не засчитываются оператору; системное подтверждение личности учитывается. Для пропуска действия указать проверенный участок, для N/A — основание неприменимости.
- Техническую ошибку помечать как ошибку обработки, сохраняя её в отчёте. Не подставлять придуманные ответы или старый результат.

В `acceptance_cases.json` находятся синтетические арифметические fixtures. Проверить нормирование шкал, N/A, отдельный флаг, нулевой знаменатель, смену веса и новый критерий через Decimal. Округлять только итог. ROUND_HALF_UP — зафиксированный выбор реализации для точной половины; PDF задаёт два знака, но не правило разрешения такой ничьей.

## 2. Ручная разметка

`starter_cases.json` содержит предварительные гипотезы. Они не являются эталоном, не входят в prompt оценщика, production lookup или cache предсказаний. Нельзя возвращать ответ по известному conversation_id.

`review_template.json` намеренно пуст. Сначала человек читает исходный диалог и чек-лист без предсказаний модели, затем заполняет ответы, evidence и основания. Второй участник проверяет; спор решается обсуждением или третьим участником. Только завершённая проверка получает `annotation_status=human_reviewed` и непустой `reviewer`. Зафиксировать версию чек-листа.

Не назначать точность по draft-ответам. Если нет валидных human_reviewed записей, метрики качества недоступны: значения null с объяснением, количество размеченных — 0. Это не 100% качества. Проверки схемы и арифметики при этом доступны.

Сомнение в продуктовых фактах хранить отдельно для ручной проверки. Не доказывать корректность консультации одной её убедительностью и не придумывать отсутствующие тарифы/процедуры. Неразрешённый спор не превращать в human_reviewed эталон.

## 3. Небольшой набор

Начать с пяти debug-диалогов. Затем расширить набор до 12–15, ориентируясь на 4–5 примеров каждого языка. До настройки prompt отложить несколько тестовых, желательно не менее трёх: разные сценарии, N/A, подтверждённая/неподтверждённая идентификация, грубый флаг, несколько вопросов и неполное завершение.

Близкие переводные шаблоны объединять в одну группу и целиком оставлять по одну сторону разделения. Перевод того же сценария не является независимым holdout. Пять разобранных debug-примеров не объявлять незнакомым тестом. После просмотра ошибок тест становится частью разработки; для следующей независимой проверки нужны новые примеры.

## 4. Метрики и охват

Для human_reviewed набора считать:

- точное совпадение ответов по каждому критерию и языку; пропущенный или ошибочный выход учитывать как несовпадение;
- отдельно правильность N/A и ошибки «N/A вместо применимого»/«применимый вместо N/A»;
- для 08 — TP/FP/FN и precision/recall с количеством положительных примеров; при нулевом знаменателе метрика null;
- MAE итогового балла на парах с корректно рассчитанными числами, обязательно показывая количество таких пар;
- coverage: обработанные без ошибок диалоги / все запрошенные, отдельно по языкам; ошибки, таймауты и пропуски сохранять в знаменателе;
- долю проверенных evidence и число неподтверждённых ссылок/выводов.

Не скрывать провалы за MAE только успешных запросов. Показывать размер размеченного набора и охват сценариев; успех на пяти примерах не даёт гарантии на контрольных десяти.

## 5. Изменение критерия и воспроизводимость

Сохранить новый конфиг; повторить расчёт и полноценную оценку на ранее не обработанных диалогах, один из которых выполняет новое условие, а другой — нет. Проверить, что новый criterion_id влияет на вывод и итог, а старый cache не подменяет запуск. При изменении смыслового правила требуется отдельная ручная разметка; старые ответы нельзя автоматически считать эталоном.

Для каждого прогона сохранить локально версии конфига/prompt, имя модели, параметры, состав набора, hash входа, результаты и ошибки. Для API дополнительно учитывать длительность и все платные вызовы, включая повторы. Повторный локальный расчёт по сохранённым ответам должен давать тот же итог.
