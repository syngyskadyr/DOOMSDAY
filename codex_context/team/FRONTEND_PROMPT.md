# Задание Codex: frontend DOOMSDAY

> Это исходное задание команды от 7 ноября 2026 года, сохранённое для дальнейшей
> поддержки. Frontend уже реализован в `frontend/public/` и опубликован в `main`;
> backend и ML также существуют. Сначала проверь текущие ветки и действующий код;
> не создавай интерфейс заново по этому заданию. Актуальные запуск и проверки
> описаны в `frontend/README.md`, `frontend/STATUS.md` и
> `codex_context/team/TEAM_START.md`. Ниже сохранены первоначальные требования.

Ты работаешь над frontend приложения Conversation Quality Analytics для 24-часового хакатона. Команда состоит из трёх человек: другой участник делает Python-оценщик, ещё один — backend. Твоя задача — реализовать интерфейс, через который можно загрузить новые разговоры, посмотреть обоснованные оценки, изменить чек-лист и пройти апелляцию. Приложение будут проверять вживую. Доведи свою часть до запуска и проверки.

## Сначала изучи проект

Прочитай действующие `AGENTS.md`, посмотри структуру репозитория, текущую ветку и `git status --short`. Сохрани существующие изменения и используй уже выбранный UI-стек. Если frontend ещё нет, создай `frontend/` с HTML, CSS и JavaScript без обязательной сборки. Код размещай вне `codex_context/`: эта папка содержит материалы задачи.

Прочитай следующие файлы относительно корня репозитория:

- `codex_context/team/HTTP_API_CONTRACT.md` — точные HTTP-маршруты, поля и состояния для связи с backend.
- `codex_context/team/fixtures/http_examples.json` — выдуманные примеры HTTP-ответов для разработки.
- `codex_context/team/HANDOFF.md` — границы задач участников.
- `codex_context/BUSINESS_RULES.md` и `codex_context/checklist.json` — смысл критериев и настройки исходного чек-листа.
- `codex_context/CONTRACT.md` — правила ответов оценщика, доказательств, N/A и расчёта.

Начни с краткого плана и затем реализуй его. Если основной backend ещё не готов, продолжай на предусмотренных синтетических примерах. Если общих файлов действительно нет, сначала перечисли отсутствующие пути; не выдумывай несовместимый контракт.

## Границы и подключение

Твоя зона — каталог frontend, его проверки и краткая инструкция запуска. Существующий backend, оценщик и общие контракты сохраняй. Все запросы приложения помести в небольшой отдельный API-клиент: экраны должны обращаться к нему, чтобы подключение backend не требовало переписывать вёрстку. Используй маршруты и JSON из `HTTP_API_CONTRACT.md`; ответ LLM из `schemas/llm_response.schema.json` сам по себе не является HTTP-ответом приложения.

Обычный режим работает с реальным API. Для разработки предусмотрен отдельный, явно включаемый режим с заметной надписью «Синтетические данные». Он использует только выдуманные примеры из `team/fixtures/http_examples.json`. Ошибка API должна оставаться видимой ошибкой; автоматического переключения на примеры нет. Локальные имитации действий в этом режиме подпиши как демонстрационные. Успешное подключение подтвердится действиями, сохранёнными backend и доступными после обновления страницы.

## Что реализовать

1. **Список диалогов.** Покажи ID, язык, канал, состояние оценки, доступный итоговый балл и отдельный признак грубой ошибки. Сделай понятные фильтры, включая подтверждённые грубые ошибки. Неопределённый флаг отображай отдельно от «нарушений нет». Предусмотри загрузку JSON с новыми разговорами через API, понятный результат импорта и переход к карточке. Пустой список — нормальное состояние, а не поломка.

2. **Карточка разговора.** Сохрани порядок, исходный текст, время и роли всех реплик: client, operator, bot, system. Отображай имена ролей понятно пользователю. По нажатию на доказательство прокручивай к соответствующему `message_id` и выделяй реплику. Для `checked_range` показывай проверенный участок: это основание для вывода о пропущенном действии. Цитаты бери из исходных сообщений. Текст разговоров выводи как текст, без исполнения вставленного HTML.

3. **Оценка.** Дай выбрать конкретную версию чек-листа и запустить оценивание. Показывай состояния ожидания, обработки, завершения, необходимости проверки и ошибки согласно контракту. Пока запрос выполняется, предотвращай случайный повторный запуск. Отображай ответы каждого критерия, объяснения, исходные и применимые веса, начисленные баллы, причины N/A, неопределённость и эпизоды нарушений. Итоги и вклады разделов получай с backend: арифметикой владеет общий scorer. `null` означает отсутствие определённого результата, а не ноль. Исходную оценку и итог после апелляций различай явно; рядом сохраняй версию чек-листа.

4. **Редактор чек-листа.** Дай изменить название, формулировку, вес, тип критерия, допустимые ответы и условия N/A; добавить новый критерий. Для шкалы редактируются допустимые ступени с описаниями и максимум, для флага — предусмотренные конфигурацией типы нарушений. Строй формы по конфигурации: исходные восемь критериев не являются постоянным ограничением. Сохранение создаёт новую версию через API. Старые результаты остаются с прежней версией; новая версия применяется при новом оценивании. Ошибки валидации backend показывай возле соответствующих полей.

5. **Апелляции.** Из конкретного критерия оператор отправляет комментарий. В отдельном представлении проверяющий видит исходную оценку, основания и обращение; подтверждает её либо изменяет допустимый ответ с обязательной причиной. Используй действия и структуру решения из HTTP-контракта. После успешного ответа backend обнови итог и историю. Новые нарушения и N/A должны иметь требуемые основания. Для демо достаточно переключения представлений оператора и проверяющего без системы входа.

6. **Звонки.** При наличии ссылки покажи простой аудиоплеер или открытие записи. Переход к времени возможен только при достоверном смещении, предоставленном API. Если соответствия времени записи и транскрипта нет, переходи к текстовой реплике и честно объясни ограничение. Если запись недоступна, текст и оценка остаются доступны.

## Порядок работы и проверка

Первый результат — запускаемые список и карточка с переходами к доказательствам. Затем подключи оценивание, редактор и апелляции. Сделай спокойный читаемый интерфейс для ноутбука: явные действия, понятные статусы, достаточно места для текста и объяснений. Статистика и декоративные графики могут подождать полного рабочего процесса.

Проверь длинный разговор, RU/KZ/EN, N/A, неизвестный балл, подтверждённый и неизвестный флаг, ошибку сервера и пустой список. Проверь добавленный критерий, изменённый вес, переход к доказательству и оформление апелляции. При готовом backend выполни полный сценарий на новом разговоре, обнови страницу и убедись, что данные сохранились. Если backend ещё недоступен, перечисли конкретно непроверенные интеграционные шаги.

В конце сообщи изменённые файлы, точные команды запуска для Windows PowerShell, выполненные проверки и их фактические результаты, способ переключить демонстрационный режим на API и оставшиеся зависимости от команды. Ключ модели хранится на сервере: frontend получает только результаты и состояние обработки.
