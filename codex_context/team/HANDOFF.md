# Договор команды: границы ИИ-компонента

Мы делаем приложение оценки диалогов операторов. Сейчас Codex реализует только Python-оценщик и инструменты его проверки. Затем команда подключит его к работающему приложению. Локальный запуск продукта допустим и должен быть воспроизводимым.

## Кто чем владеет

| Участник | Его зона | Результат для команды |
|---|---|---|
| ИИ/ML | `src/cqa_eval/` либо согласованный аналог, собственные тесты и документация; инструкция модели, валидация и общий расчёт баллов | Две импортируемые функции и CLI |
| Бэкенд | API приложения, импорт данных, постоянное хранение, версии чек-листов, запуск оценивания, апелляции | Соединяет интерфейс с оценщиком; использует общий scorer |
| Фронтенд | Список и карточка диалога, доказательства, результаты, редактор критериев, апелляции | Пользовательский интерфейс по согласованному контракту |

Не меняем чужие файлы. Работаем в своих ветках и согласованных каталогах. Общий контракт — `CONTRACT.md`; точная форма ответа — `schemas/llm_response.schema.json`. Изменения контракта сначала согласуем втроём.

## Два интерфейса

**`evaluate_dialogue(dialogue, checklist)`** получает один полный диалог и конкретную версию чек-листа. Возвращает валидированные ответы по критериям, объяснения, сообщения-доказательства, проверенные участки, причины N/A и выявленные нарушения. Формат результата и параметров — в `CONTRACT.md`. Это обычный Python-компонент внутри бэкенда; отдельный ML-сервис не требуется.

**`calculate_score(checklist, results)`** получает валидированные результаты критериев по контракту и детерминированно рассчитывает баллы. ИИ-участник реализует функцию и тесты; бэкенд импортирует её. Повторную формулу во фронтенде или бэкенде не пишем: один расчёт используется и после оценки, и после решения по апелляции.

`m001` — первое сообщение исходного `transcript`, `m002` — второе. Индексы назначаем до фильтрации; роли и timestamps сохраняем. Бэкенд и фронтенд используют те же идентификаторы для перехода к доказательствам. ISO-время само по себе не задаёт позицию воспроизведения аудио.

Техническая ошибка не становится N/A. `needs_review` с `answer: null` отображается как необходимость проверки; неизвестный весовой ответ оставляет общий балл неопределённым. Флаг грубой ошибки хранится отдельно от балла, без веса; неизвестный флаг не равен отсутствию нарушения.

## Что нужно для параллельного старта

В комплекте уже есть общий пример входа `eval/synthetic_dialogue.json` и **явно синтетический** валидный результат `eval/synthetic_response.json` (пути от корня codex_context). Он нужен фронтенду для вёрстки и бэкенду для подключения; это не ответ модели и не доказательство её качества. Такой пример живёт в тестовых материалах, а не в production-оценщике.

Бэкенд начинает с чтения `data/dev.json`: записи находятся в `data.records`. Фронтенд показывает список, переписку, таблицу критериев и доказательства. ИИ-участник параллельно заканчивает офлайн CLI, валидацию, scorer и адаптер модели. Когда доступен ключ, соединяем реальную оценку одного диалога с приложением.

Секреты провайдера остаются на стороне бэкенда. ИИ-компонент использует настройки окружения; интерфейс не получает API-ключ. Входные данные и ответы не используются как скрытая таблица готовых оценок. Ручная разметка подключается только при проверке качества.

## Что бэкенд обеспечивает дальше

Редактирование создаёт новую версию чек-листа. При оценивании бэкенд передаёт именно её; новый критерий действительно доходит до модели. Старый результат остаётся связан со старой версией, а кеш не смешивает версии.

Апелляция сохраняет исходный ответ, решение, причину и итоговый ответ. После изменения бэкенд повторно проверяет допустимость результатов и вызывает общий scorer. Для грубых ошибок сохраняются исходный и итоговый флаги и связанные эпизоды; изменение флага не обнуляет числовой балл.

## Что показать перед объединением

- ИИ: успешные офлайн-команды и тесты; отдельно — результат единственного реального запуска, если он был.
- Бэкенд: открытие диалога, вызов оценщика, сохранение и повторное чтение результата.
- Фронтенд: корректное отображение ответа, N/A, необходимости проверки и технической ошибки; переход к доказательствам.

Точность оцениваем по проверенной разметке. Интерфейс, редактор и апелляции тоже обязательны для финального продукта. Красивые звуковые волны и облачный хостинг к обязательствам этого компонента не относятся.
