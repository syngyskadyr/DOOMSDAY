# Совместная интеграция DOOMSDAY

Состояние сверено 8 ноября 2026 года: в `origin/main` на коммите `3a22336`
уже есть backend, frontend и ML-компонент. Frontend находится в
`frontend/public/`: это HTML, CSS и JavaScript без обязательной сборки.
Дополнения backend для автозагрузки `.env`, CLI и описания API находятся в
[PR #3](https://github.com/syngyskadyr/DOOMSDAY/pull/3) из `feat/backend`.
Инструкция `.env` ниже относится к версии с этими дополнениями.

`BACKEND_PROMPT.md` и `FRONTEND_PROMPT.md` — исходные задания команды. Используйте
их как требования при поддержке существующего приложения. Текущие команды и
фактические ограничения смотрите также в `backend/README.md`, `backend/STATUS.md`,
`frontend/README.md` и `frontend/STATUS.md`.

## Сначала проверь локальную копию

Откройте всю папку DOOMSDAY в VS Code и проверьте текущую ветку, `git status`,
удалённые ветки и историю. `git fetch origin` обновляет сведения о GitHub,
но не переключает ветку и не добавляет frontend в рабочую папку `feat/backend`.
Отсутствие локального каталога `frontend/` не означает, что его нет в `main`.

Для совместной проверки используйте согласованную ветку, содержащую актуальную
`main` и нужные изменения PR #3. Объединение выполняет назначенный участник после
проверки. Сохраняйте незакоммиченные и неотслеживаемые файлы; не заменяйте рабочую
копию архивом и не переписывайте чужую историю. Для отдельной проверки можно
использовать другую копию репозитория.

## Локальный запуск

Из корня согласованной копии проекта, Python 3.11+. В Windows PowerShell:

```powershell
py -3 -m venv backend/.venv
& .\backend\.venv\Scripts\python.exe -m pip install -r requirements-backend.txt -e .
& .\backend\.venv\Scripts\python.exe -m backend --host 127.0.0.1 --port 8000 --frontend frontend/public
```

Linux:

```bash
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r requirements-backend.txt -e .
backend/.venv/bin/python -m backend --host 127.0.0.1 --port 8000 --frontend frontend/public
```

Если окружение уже подготовлено, используйте его Python и переходите к запуску.
Откройте `http://127.0.0.1:8000/`; API доступен по `/api`, интерактивное описание —
по `/docs`. Отдельный frontend-сервер и `npm run build` для текущего интерфейса
не требуются. Запускайте один процесс backend без hot reload.

При наличии `codex_context/data/dev.json` сервер импортирует его при запуске.
Без DEV можно начать с пустым списком и загрузить JSON через интерфейс. Флаг
`--no-dev` отключает автоимпорт, а `--dev <путь>` выбирает другой локальный файл.
Постоянная база по умолчанию — `backend/data/doomsday.sqlite3`.

## Настройки модели

С изменениями PR #3 backend читает необязательный `.env` из корня репозитория.
Если файла ещё нет, создайте его из `backend/env.example`, сохранив существующие
локальные настройки. В PowerShell:

```powershell
if (-not (Test-Path .env)) { Copy-Item backend/env.example .env }
```

Заполните локально `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_STYLE`
по настройкам провайдера команды; подробности — в `CQA_README.md`. Переменные
процесса имеют приоритет над `.env`. Путь можно выбрать через `--env-file <путь>`,
чтение отключить через `--no-env-file`. Если работаете на `main` без PR #3,
задайте переменные в окружении процесса: эта версия автоматически `.env` не читает.

Без настроек LLM импорт, чтение и редактор работают; новый запуск оценки
возвращает явную ошибку недоступности. `evaluator_status=ready` в `/api/health`
не доказывает доступность модели у провайдера. Реальный платный вызов выполняйте только после согласования
с ответственным ML-участником. Тестовый оценщик подключается явно в тестах и не
является автоматическим резервом приложения.

## Кто что поддерживает

| Роль | Своя зона | Ответственность |
|---|---|---|
| ML | `src/cqa_eval/`, ML-тесты и документация | Оценка разговора, валидация ответа, общий scorer и настройки провайдера |
| Backend | `backend/`, backend-тесты и документация | Импорт, API, SQLite, версии чек-листов, задания и апелляции |
| Frontend | `frontend/`, frontend-тесты и документация | Список, карточка, доказательства, редактор и действия через API |

Общий HTTP-контракт — `team/HTTP_API_CONTRACT.md` относительно `codex_context/`;
контракт Python-оценщика — `codex_context/CONTRACT.md`. Формула расчёта одна:
backend использует общий scorer и после оценки, и после решения апелляции.
Изменения общих контрактов согласовывайте, сохраняйте границы из `team/HANDOFF.md`.
Троим не нужно повторно выполнять `codex_context/CODEX_PROMPT.md`: это задание ML.

Для продолжения работы передайте Codex свою роль, конкретное изменение и текущую
ветку. Попросите сначала прочитать соответствующее исходное задание, действующие
инструкции проекта и текущий код, затем проверить нужный сценарий. Не поручайте
повторно создавать уже реализованные части.

Каждый сохраняет проверенные изменения своей зоны отдельным коммитом и отправляет
ветку на GitHub. Назначенный участник проверяет и объединяет PR; остальные
получают изменения согласованной ветки через Git. Сессии Codex и открытый VS Code
не синхронизируют локальные файлы между компьютерами. Не используйте force push
для обычной совместной работы.

## Данные и проверка перед демонстрацией

DEV в `codex_context/data/dev.json` исключён из Git, поэтому обычный clone может
не содержать данные. Передавайте их отдельно. Не добавляйте в публичный Git
исходные разговоры, `.env`, ключи, базу, результаты, аудио или весь архив команды.
`team/fixtures/http_examples.json` содержит только явно синтетические примеры
формата; опубликованный frontend работает с реальным API и не подменяет ошибки
этими примерами.

Проверьте полный процесс на новом разговоре: импорт → оценка выбранной версией →
просмотр оснований → фильтр подтверждённых грубых ошибок → создание и рассмотрение
апелляции → добавление критерия → новая оценка. Обновите страницу и перезапустите
сервер: разговоры, старые версии и результаты должны сохраниться. Не выводите
закрытые разговоры и настройки провайдера в отчёт. Отдельно зафиксируйте результаты
офлайн-тестов, проверки с тестовым оценщиком и реального вызова модели.
