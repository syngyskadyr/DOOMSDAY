# Codex: backend DOOMSDAY / CQA

> Это исходное задание команды от 7 ноября 2026 года, сохранённое для дальнейшей
> поддержки. Backend и ML уже реализованы, frontend опубликован в `main`.
> Сначала проверь текущее состояние веток и действующий код; не создавай
> приложение заново по этому заданию. Актуальные запуск и интеграция описаны в
> `backend/README.md`, `backend/STATUS.md` и `codex_context/team/TEAM_START.md`.
> Ниже сохранены первоначальные требования и границы ответственности.

Ты работаешь в локальном репозитории DOOMSDAY. Реализуй backend работающего приложения для оценки разговоров операторов по изменяемому чек-листу. Команда из трёх человек участвует в хакатоне на 24 часа: другой участник делает frontend, третий — Python-компонент LLM-оценщика. Твоя задача — соединить их через API, постоянное хранение и полный процесс оценки и апелляции. Нужен воспроизводимый локальный запуск.

## 1. Прочитай контекст и проверь проект

Сначала прочитай действующие инструкции `AGENTS.md`, проверь структуру проекта и `git status --short`. Сохрани незакоммиченные изменения. Работай в своей ветке `feat/backend`; если ветка уже подготовлена, используй её. Не переключай ветку с чужими изменениями и не выполняй разрушительные Git-команды.

Прочитай следующие файлы относительно корня проекта:

- `codex_context/team/HTTP_API_CONTRACT.md` — точные маршруты, запросы, ответы и состояния HTTP API;
- `codex_context/team/HANDOFF.md` — границы ответственности;
- `codex_context/CONTRACT.md` — отдельный контракт Python-оценщика и расчёта;
- `codex_context/BUSINESS_RULES.md`, `codex_context/checklist.json` и `codex_context/schemas/llm_response.schema.json`;
- `codex_context/team/fixtures/http_examples.json` — явно синтетические примеры HTTP-формата;
- `codex_context/README_START.md` и `codex_context/env.example`.

Используй материалы внутри `codex_context`, а не устаревшие одноимённые копии в корне. Не подменяй HTTP-ответ сырым JSON модели: преобразование между ними выполняет backend. Если в проекте уже есть API, сохрани полезную реализацию и приведи внешнюю границу к общему контракту. Содержимое DEV достаточно проверить программно; не выводи все разговоры в чат.

Кратко обозначь план и затем реализуй доступную работу. Обычные решения принимай самостоятельно. Отсутствие готового оценщика не должно останавливать импорт, хранение, чтение и редактор чек-листа.

## 2. Границы и простой стек

Основная зона изменений — `backend/` либо уже существующий каталог сервера. Свои зависимости, тесты и инструкции размещай в явно обозначенных backend-файлах. Не переписывай `frontend/`, ML-модуль, его промпты, исходный чек-лист и чужие тесты. Согласованный HTTP-контракт не меняй молча; проблему опиши отдельно с конкретным несовпадением.

Если серверного стека ещё нет, используй один Python/FastAPI-сервер и SQLite. При наличии frontend раздавай только его публичный каталог с того же origin; не публикуй весь репозиторий или `codex_context`. Существующий стек сохраняй. Для этого прототипа достаточно локальных фоновых задач: без отдельного ML-микросервиса, Redis, Celery и системы аккаунтов.

## 3. Данные и API

Реализуй все серверные операции из HTTP-контракта: состояние сервера, импорт, список и карточку диалога, фильтры, версии чек-листа, запуск и получение оценки, создание и рассмотрение апелляции. Порядок и форму полей бери из контракта, не придумывай параллельные маршруты.

Импорт нормализует JSON организаторов с `data.records`, массив записей либо одну запись. Для исходной оболочки проверь `isSuccess`. Локальный файл `codex_context/data/dev.json` содержит 65 разговоров, но число 65 и известные ID не являются ограничениями программы. При отсутствии файла объясни, как загрузить данные; чтение чужого компьютера не предполагается.

Проверяй пакет целиком до записи. Повтор идентичного диалога пропускай; изменённое содержимое под существующим ID возвращает HTTP 409 без частичного импорта. Некорректный вход возвращает понятную ошибку валидации. Сохраняй исходные текст, роли, порядок, timestamps и audio_url. Назначай `m001`, `m002` и далее по исходному индексу, включая bot/system. Повторы и ошибки распознавания не удаляй. Не выдумывай смещения аудио из ISO-времени.

Храни диалоги, версии чек-листа, задания, оценки и апелляции в SQLite с сохранением после перезапуска. Достаточно компактной схемы и JSON-полей для снимков. Фильтр грубых ошибок должен использовать поле и область результата, оговорённые контрактом; неизвестный флаг не равен `false`.

## 4. Подключи компонент ML через адаптер

Найди фактические публичные функции ML-модуля. Ожидаются `evaluate_dialogue(dialogue, checklist)` и `calculate_score(checklist, results)`; учитывай реальную синхронность, типы и обёртки. Сделай небольшой адаптер в своей зоне, не переделывая чужую реализацию. Одну и ту же чистую функцию расчёта используй после оценки и после пересмотра.

Если модуль или настройки провайдера отсутствуют, остальные функции приложения должны работать. Запуск реальной оценки возвращает явный HTTP 503 с объяснением недоступности. Не заменяй недоступный оценщик фиктивными баллами. Синтетический оценщик разрешён только как явно подключённая тестовая зависимость, не как автоматический резерв production-режима.

При создании задания зафиксируй диалог и неизменяемый снимок выбранной версии чек-листа. HTTP-запрос запуска не должен ждать долгий LLM-вызов. Сохраняй переходы состояния задания по контракту. При перезапуске помечай незавершённые локальные задания понятной ошибкой; не оставляй вечное «выполняется». Повторы API делегируй ограниченному механизму оценщика, не добавляй второй бесконечный цикл.

Проверяй результаты перед сохранением. Ошибка провайдера или JSON — ошибка задания, не N/A и не нулевой балл. `needs_review` сохраняй отдельно. Сохраняй модель, версии, хеши, доступный usage, число вызовов и стоимость; неизвестная стоимость остаётся `null`. Если реализован кэш, учитывай содержимое диалога, чек-лист, промпт и модель и явно отмечай попадание.

## 5. Версии и апелляции

Редактирование и добавление критерия создаёт новую версию конфигурации. Валидируй веса, типы, шкалы, допустимые ответы, N/A и ссылки на секции. Не зашивай восемь критериев. Новая версия должна реально передаваться оценщику; старые оценки остаются на своих снимках. Конкурирующие изменения обрабатывай по правилам HTTP-контракта.

Апелляция привязана к сохранённой оценке и критерию, содержит комментарий. Решение проверяющего подтверждает ответ либо заменяет его допустимым значением с причиной и нужными доказательствами. Проверяй замену по снимку исходного чек-листа, затем пересчитывай итог общим scorer. Сохраняй неизменяемый исходный результат, журнал решений и текущий финальный результат. Отклоняй повторное рассмотрение уже закрытой апелляции. Флаг грубой ошибки пересматривается отдельно и не обнуляет числовой балл.

## 6. Проверка и передача команде

Секреты находятся только в окружении сервера. Не отдавай ключи, подписанные URL или содержимое `.env` в диагностике. DEV, база, результаты и аудио не должны попасть в публичный Git. Не запускай платные оценки самовольно: реальный smoke-вызов сейчас принадлежит ML-участнику.

Проверь значимые сценарии с подставным тестовым оценщиком: импорт нового диалога и конфликт ID; сохранение после перезапуска; запуск, ошибка и чтение оценки; новая версия и старый снимок; апелляция с пересчётом без потери оригинала; фильтр грубых ошибок. Используй общий scorer, не копируй формулу в тестовую инфраструктуру.

Первый результат для frontend — работающие список, карточка и чек-лист на реальных импортированных данных. Затем подключи оставшиеся операции. В итоговом отчёте дай точные команды PowerShell для установки и локального запуска, изменённые файлы, результаты фактически выполненных проверок и конкретные оставшиеся зависимости от ML. Чётко раздели проверку с тестовой зависимостью и реальный вызов модели.
