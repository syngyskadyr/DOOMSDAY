# Контракт ML-оценщика, версия 1

Это инженерный формат команды, не обязательная схема организаторов. Соблюдайте его одинаково в AI-модуле и backend. Источник формы ответа — schemas/llm_response.schema.json; допустимые ответы конкретного критерия — переданный checklist.json.

## Вход

evaluate_dialogue(dialogue, checklist) получает одну запись организаторов и текущую конфигурацию. CLI извлекает записи из data.records при isSuccess=true. Сохраняет conversation_id, channel, language, transcript и audio_url.
Сообщения получают message_id m001, m002 и далее по исходному индексу, включая client, operator, bot, system. Не удалять повторы, не менять порядок, текст или timestamp. Поле source_index можно хранить отдельно. Нельзя выдумывать смещение аудио из ISO-времени.

Для API готовится один диалог целиком. Запись аудио не скачивается по умолчанию и не передаётся текстовой модели. Исходные audio_url сохраняются для будущего плеера, но не нужны в текстовом запросе модели.

## Ответ модели

Объект содержит conversation_id, checklist_version (строка) и criteria. На каждый критерий текущего чек-листа должен приходиться ровно один элемент. Фиксированное число восемь применимо только к исходной конфигурации.

Элемент criteria:

- criterion_id — строковый ID.
- status — evaluated или needs_review.
- answer — yes/no/na либо число из конфигурации; null только при needs_review.
- reason — короткое пользовательское объяснение, без запроса скрытых рассуждений модели.
- evidence_message_ids — реальные ID подтверждающих реплик.
- checked_range — null либо объект start_message_id/end_message_id; для пропущенного действия указывает проверенный участок, включая место ожидаемого действия.
- na_reason — обязательная непустая причина при answer=na, иначе null.
- uncertainty — непустое описание недостающего основания при needs_review; иначе null либо явно названная оговорка.
- violations — эпизоды грубого нарушения: type, reason, evidence_message_ids. Тип должен входить в flag_types соответствующего критерия. Для остальных критериев пустой массив.

Для оценённого flag=yes violations не пуст, каждый эпизод содержит основание. Для flag=no violations пуст. Общий флаг — производное поле обёртки, его не нужно доверять арифметике LLM.

## Семантическая валидация поверх JSON Schema

Проверить совпадение conversation_id и версии, полноту и уникальность критериев, разрешённые ответы, N/A, допустимые номера и порядок диапазонов, типы нарушений. Числа не принимаются вместо строк yes/no и наоборот; boolean не является числовой ступенью.
В каждой оценённой строке должно быть доказательство или корректный проверенный диапазон. Для omitted action используйте диапазон, а не придуманную цитату отсутствия. Разрешены доказательства из client/bot/system, когда они подтверждают контекст; выполнение действия оператора не приписывается ему по реплике другого участника.
Существование message_id не доказывает смысловую правильность оценки. Это отдельно проверяется по рабочей разметке команды.
Структурированный вывод API использовать, если конкретный провайдер его поддерживает. Полная схема файла — контракт проверки в приложении; её нельзя без проверки совместимости считать поддерживаемой каждым API.

## Расчёт

calculate_score(checklist, validated_results) — чистая функция без API-вызова. Для binary yes/no используются доли 1/0; для scale — answer/scale_max. Flag не входит в вес. Исключаются только разрешённые na.
Итог = 100 * sum(weight * fraction) / sum(applicable weights). Округлить лишь финальный итог до двух знаков, используя Decimal и документированное ROUND_HALF_UP. При нулевом применимом весе total_score=null.
На изменённом чек-листе нормализуйте положительные применимые веса до 100; это принятое решение команды. Отклоняйте некорректные веса/ступени/конфигурации до вызова модели.
Если хотя бы один весовой критерий needs_review, окончательный total_score=null. Не превращать неизвестность в na и не уменьшать знаменатель. Для неоценённого флага возможен численный итог по завершённым балльным критериям, но общий статус остаётся needs_review, а флаг при отсутствии подтверждённого нарушения — null.

Чистый scorer возвращает total_score, applicable_weight, rows с base_weight/effective_weight/earned_points и суммы вкладов секций. Возвращайте также признак отсутствия применимых балльных критериев. В тестовых fixtures строки ответов могут быть упрощены; production scorer принимает только проверенный полный ответ.

## Обёртка и интеграция

Backend-ready результат объединяет validated assessment, calculation, critical_error и metadata. Metadata: фактическая модель, hash диалога/чек-листа/инструкции, версии, длительность, число вызовов и повторов, доступный usage. Если цена или usage неизвестны, стоимость null с объяснением; отсутствие данных не означает бесплатность.
Никаких токенов API и подписанных URL в логах или выводе. Неизвестные модельные тарифы не придумывать. Учитывать все вызовы оценки, включая исправление формата.
API-ошибка и окончательно невалидный JSON — ошибка обработки, а не полученная оценка. Использовать ограниченные повторы; не превращать сбой в нулевой балл.

## Изменения и воспроизводимость

Чек-лист — аргумент, ID критериев не должны быть ветками if в production-коде. Новые правила реально включаются в запрос. Кэш должен зависеть как минимум от содержимого разговора, чек-листа, инструкции и модели; явно записывайте cache_hit.
Фиксировать поддерживаемые настройки генерации, но не обещать битовую идентичность независимых LLM-запусков. Backend хранит исходную оценку отдельно от решений по апелляциям и финального результата. При апелляции по flag меняется флаг, но численный итог не обнуляется.
